我给我的终端装了块霓虹招牌

编程 2026-07-29 · 阅读约 3 分钟

换了台新电脑之后,我的终端空无一物。干净得像毛坯房,亮得像个刚出厂的灯泡。每次打开它,我都觉得自己在加班,而不是在开始一天的工作。

直到那个凌晨三点,我受够了。我决定:给我的终端装一块霓虹招牌。

开工:三行 echo,一颗赛博心

方案很简单——在 ~/.bashrc 里用 printf 打一段 ASCII 艺术大字,再用 ANSI 转义码上色。荧光绿配品红,像赌场门口的招牌,像霓虹灯管组成的欢迎语:

printf '\e[38;5;46m%s\e[0m\n' \
  '███████╗ ██████╗ ██╗   ██╗███╗   ██╗'
printf '\e[38;5;201m%s\e[0m\n' \
  '██╔════╝ ██╔══██╗██║   ██║████╗  ██║'
printf '\e[0;33m>>> BASS DIARY TERMINAL v2.0 <<<\e[0m\n'

保存,重开终端。字出来的那一刻,屏幕亮了,我的心情也亮了——那种亮度,Windows 的深色模式都给不了。

后果

同事路过,看到我屏幕上冒着绿光的方块字,问我是不是中毒了。我说不是,这是企业文化。后来我把 PS1 也换成了霓虹风格,现在敲每条命令都像在点歌。

效率工具不必高效。快乐,也是一种生产力。

如果你想试:记住转义码是 \e[38;5;NUMBERm,256 色随你挑。别挑超过三种,否则你会发现自己盯着终端看了四十分钟,一条命令都没敲。

把 ToDo 列表当客户骂

效率 2026-07-18 · 阅读约 3 分钟

待办事项列表,是唯一一件我每天辱骂三遍却仍然依赖的生产力工具。它记下了我所有想做的事,以及我不想做的理由。

直到有一天我悟了:优先级排序不用学什么 GTD,不用四象限,不用番茄钟。你只需要把列表里的每一项,当成一个正在打电话投诉的客户。

方法论:谁嗓门大谁先做

紧急程度 = 客户现在骂得有多凶。重要程度 = 这个客户会不会一直骂下去。于是:

P0 = 已经在投诉了。P1 = 正在准备投诉。P2 = 还没人发现。P3 = 永远不会有人发现,删了吧。

这个模型的妙处在于它毫不留情。以前我舍不得删待办——"万一哪天用得上呢"。现在我会想:这个客户三年没来电话了,他大概已经换供应商了。

Deadline 不是截止日期,是客户从「再等等」变成「你完了」的那个转折点。

副作用

把列表当客户之后,我删起待办来毫无愧疚感。列表从四十七项瘦身到九项,剩下的每一项都理直气壮。拖延症没有痊愈,但它学会了看人脸色。

顺带一提:这个方法对真实的客户也有效。区别是,真实的客户你不会删除,你只会加急。

手写 CSS 边框阴影的一年

设计 2026-07-02 · 阅读约 4 分钟

box-shadow: 6px 6px 0 black; 这一条规则,我写了整整一年。开始只是觉得好看,后来越写越觉得它是一句人生哲学。

模糊阴影在撒谎——它假装世界是软绵绵的,假装物体悬浮在空中,假装一切都像照片一样真实。但屏幕不是现实,数字世界不需要拟物,它需要诚实。

这一年我学到的三件事

第一,圆角是懦弱,硬边框是态度。圆角说"我尽力显得友好",直角说"我就是这样,你看着办"。人类对直角有一种莫名其妙的信任感——不信你去看地铁站牌。

第二,颜色要像爆米花一样大声。一年前我还用 #f5f5f5 配 #999,现在我用荧光黄配电光蓝。前者是"我在吗?",后者是"我在!"。

第三,阴影方向必须永远一致,世界才不会崩塌。光从左上角来,所有投影都往右下走。这是整个设计系统里最不容商量的规矩——混乱的设计千奇百怪,自洽的设计只有一种。

一次只吼一件事。留白不是浪费,是让吼声有回声。

下一年

明年,我要把手写体也请进页面。老板看完说像小学生作业,我说这叫笔迹,叫人格。他沉默了三秒,然后让我把边框再加粗一像素。

我照做了。你看到的这些粗边框,有一部分是他的功劳。

再见,我的 512MB 服务器

随笔 2026-06-20 · 阅读约 4 分钟

今天凌晨一点十七分,我把运行了七年的服务器关机了。它最后一条日志是我写的:Goodbye, and thanks for all the fish. 然后是我手打的 shutdown now。

2019 年我租下它:512MB 内存,一颗老双核,一个 25G 的盘。我往里面塞了 nginx、一个博客、一个机器人、一个监控脚本,外加 swap 当内存用。它像一间只放得下一张床的出租屋,住了五口人。

它的习惯

它的内存长期占用 99%。一开始我天天看监控,后来我学会了不看监控——就像你知道那只猫把冰箱当窝之后,就不再试图纠正它。它稳定得像一个倔强的老门卫:风雪无阻,就是从来不升级。

七年里它被我 apt upgrade 炸过两次,被我自己写崩的脚本连累宕机三次。每次它都自己挺过来了——准确说,是每次都有个半夜醒来的我,ssh 进去,把服务一个个拉起来,像给熬夜加班的同事递咖啡。

告别清单

备份。导出。关机。拔卡。七年,压缩成一个 300MB 的 tar 包,躺在我的移动硬盘里,像一本合上的日记。

按下电源键的那几秒,风扇声一点点安静下来。我第一次发现,原来它平时一直在说话——只是我们都不懂,那叫 24×7 的陪伴。

我们总说数据无价。其实机器,也是有性格的。

新服务器是四核 8G,速度快得像换了个世界。但它没有名字,没有七年,没有那些 log 里被修复过的旧 bug 的故事。所以我写了这篇文章——好让它知道,有人记得它。

辛苦了,老朋友。你退休了。

用 SQL 写情书

整活 2026-06-01 · 阅读约 3 分钟

写情书很难。真诚、具体、还要可执行——这跟写需求文档是一回事。所以,程序员自有程序员的解法。

需求分析:一封合格的情书,要能查得出来,删不掉,还自带事务回滚(万一对方拒绝,整个事务直接 ROLLBACK,不留痕迹)。

第一版(粗糙,但能用)

SELECT * FROM 我的心
WHERE 对象 = '你'
  AND 永远 = TRUE;

跑了一遍,报错:永远 没有默认值。我补上了:

ALTER TABLE 我的心 ADD COLUMN 永远 BOOLEAN DEFAULT TRUE;

这次跑通了。返回了一行,是我。

优化

后来我做了三处优化:加索引——天天想你就是给它建索引,查询速度快到毫秒级;加事务——BEGIN; 一辈子; COMMIT; 要么一次提交,要么全部回滚;加注释——每一行旁边都写着"别删,这很重要"。

SELECT 你 FROM 我心 WHERE 永远 = TRUE;

彩蛋

情书送出去一周后,她回了消息。只有一行:

DROP TABLE 单身;

我盯着这行命令愣了半天——她没学过 SQL 啊?后来才知道,她照着我的格式,让 GPT 帮她把"我想和你在一起"翻译成了这句。

我很确定,我们之间的事务,已经 COMMIT 了。
